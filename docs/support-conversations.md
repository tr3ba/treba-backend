# Переписки поддержки

Покупатель открывает «Чат з TREBA» или нажимает «Задати питання» в карточке товара. Для переписки нужен настоящий аккаунт API; демонстрационные аккаунты магазина не переносятся в базу автоматически. В `/support` админки Administrator, Manager и Moderator отвечают на личные обращения TREBA, а Seller — на вопросы о собственных товарах.

## Переписки

- `CHAT` — личная поддержка без заказа. У покупателя одна активная личная переписка; после закрытия можно начать новую.
- `QUESTION` — приватный вопрос о товаре или заказе. По одному товару у покупателя одна активная переписка. Другие покупатели и продавцы доступа к ней не получают. Новое обращение по товару требует активного товара, история сохраняется после снятия товара с продажи.
- `RETURN` — прежний процесс возврата всего доставленного заказа, обязательно с `OrderId`.

Список и переписка обновляются каждые пять секунд. Интерфейс магазина приостанавливает опрос скрытой вкладки и обновляется при возвращении. В админке есть очередь `?view=unread`, предпросмотры последних сообщений и внутренние заметки. Внутренние заметки не попадают покупателю, в его предпросмотр или счётчик непрочитанного и не считаются ответом поддержки для SLA.

## API

`/api/v1/support` принимает и возвращает только обращения, доступные текущему аккаунту. Покупатель видит свои переписки. Administrator и Manager видят обращения TREBA и вопросы/возвраты по заказам, Moderator — только личные чаты TREBA. Вопросы с `ProductId` доступны исключительно покупателю и активному Seller магазина этого товара. Сотрудники TREBA не могут читать их, отвечать, отмечать прочитанными или менять статус. Продавцы не имеют доступа к личным чатам TREBA и вопросам чужих товаров. Неактивный магазин или приостановленный продавец теряет доступ к ответам.

- `POST /` принимает `Kind`, `Subject`, `Message`, необязательные `OrderId`, `ProductId`, `ClientRequestId`. ID покупателя определяется по авторизации, а в обращении по заказу — по владельцу доступного заказа.
- `GET /` поддерживает страницу по 12 переписок, поиск, `kind`, `status`, `productId`, `view=open|overdue|unread`.
- `GET /{id}` возвращает контекст и последние 50 доступных сообщений в хронологическом порядке, с `HasEarlierMessages`.
- `GET /{id}/messages?before={messageId}` загружает до 50 более ранних сообщений. Курсор должен принадлежать доступной переписке и быть видимым текущему аккаунту.
- `POST /{id}/messages` принимает `Message`, `Internal`, `ClientMessageId`. Внутренние заметки доступны только сотрудникам. Ответ сотрудника переводит новое обращение в работу.
- `POST /{id}/read` принимает `MessageId` последнего показанного сообщения. Чтение не меняет порядок очереди или версию статуса. Отметка сотрудников общая для команды поддержки; отметка покупателя отдельная. Конкурентные обновления защищены проверкой версий.
- `PATCH /{id}/status` доступен отвечающей стороне своей очереди. Возвраты по заказам остаются исключительно у Administrator и Manager. Закрытая переписка остаётся в истории и не принимает новые сообщения.

UUID `ClientRequestId` и `ClientMessageId` позволяют безопасно повторить отправку после сетевого сбоя. Повтор с тем же ID и другим текстом отклоняется. Уникальные частичные индексы защищают активные личные и товарные переписки от конкурентного создания.

В магазине маршрут товара использует slug, а `ProductId` API — UUID. Поле `Product.backendId` сохраняет UUID из каталога; `TicketRow.ProductSlug` возвращает адрес для ссылки обратно на карточку.

## Схема и публикация

Миграция `20261020104554_AddSupportConversations` делает `OrderId` необязательным, добавляет ссылку на товар, отметки прочтения и индексы. Существующие обращения сохраняются. Ручной идемпотентный SQL: `scripts/sql/20261020-support-conversations.sql`, применяется после предыдущей операционной миграции.

Обычное развёртывание API применяет миграцию через `--migrate-admin-operations` до переключения контейнера. Затем публикуется связанная версия `tr3ba/treba-frontend`. Обратная миграция явно останавливается, если есть переписки без заказа: их нельзя молча удалить или заменить фиктивным заказом.

Проверено 229 тестами API/админки с PostgreSQL 18. Проверки охватывают разделение очередей через HTTP и сервис, чужие товары, приостановленного продавца, приватность заметок, непрочитанные сообщения и статусы. Обновление предыдущей схемы и повторное применение SQL проверены при добавлении переписок.
