## Заказы и остатки

- `/orders` содержит поиск по номеру, имени, телефону и email, фильтр статуса, даты и пагинацию. Условия хранятся в URL. Конечная дата включает весь выбранный день по часовому поясу панели.
- `/orders/{id}` показывает состав, адрес, суммы, комментарий и историю. Изменение статуса требует актуальной версии. История, остатки и статус записываются одной операцией `SaveChanges`, включая аудит сотрудника.
- Покупатель берётся из действующей сессии. Переданные клиентом цены, скидки, имена, SKU и снимки товаров не используются: сервис читает актуальный опубликованный каталог. Доставка сейчас фиксированная — 50 UAH, как и в прежнем сервисе; промокод на бесплатную доставку из существующего сервиса может обнулить её.
- `ProductVariant.StockQuantity` — единый доступный для продажи остаток. Новый резерв сразу уменьшает его, подтверждение оплаты не списывает товар повторно. Отмена до отправки или приём полного возврата восстанавливают количество ровно один раз. Изменение остатка обновляет версию карточки товара, чтобы открытый ранее редактор не перезаписал остаток устаревшим значением.
- Неоплаченный резерв действует 30 минут. Фоновый обработчик раз в минуту отменяет просроченные заказы; повторная обработка и одновременная оплата защищены проверками конкурентных изменений.
- Получение оплаты подтверждает администратор или менеджер вручную. Интеграции с платёжным провайдером и автоматического денежного возврата нет.
- Продавец видит только собственные позиции и их суммы. В заказе с несколькими продавцами общий статус меняет сотрудник. Для заказа одного продавца продавцу доступны этапы обработки и доставки, но не подтверждение оплаты и отмена. Служебные комментарии истории продавцам не передаются.

Разрешённая последовательность: `AWAITING_PAYMENT → PAID → CONFIRMED → PROCESSING → READY_FOR_SHIPMENT → SHIPPED → DELIVERED → COMPLETED`. Отмена с обязательной причиной доступна сотрудникам до отправки; покупателю — до оплаты. Возврат проходит через обращение, а не произвольное переключение статуса.

Старые складские записи `Inventory` не объединяются с каталогом автоматически. До обновления выполните **только читающий** [отчёт сверки](../scripts/sql/20261020-stock-reconciliation.sql). Если остались активные/подтверждённые резервы с ненулевым `WarehouseId`, их нужно сверить с каталогом отдельно: новый процесс остановит такое действие с объяснением, сохранив данные. Новые корректировки склада используют пустой `WarehouseId`; отдельное создание/подтверждение/снятие резерва через старые маршруты отклоняется — эти действия выполняются вместе с заказом.

## Акции и промокоды

- `/loyalty`: список, поиск по названию/коду, фильтр статуса, редактор.
- Поддерживаются процентная и фиксированная скидка, сроки, максимальная скидка, минимальная сумма заказа и ограничения по товару, точной категории, бренду и продавцу. Несколько ограничений применяются вместе.
- Для применения нужен промокод. На акцию можно создать до 30 кодов с общим и персональным лимитами. Нулевой лимит означает отсутствие ограничения.
- Черновик не активируется сам. Статус `SCHEDULED` включает автоматический запуск по датам; `ACTIVE` и `SCHEDULED` автоматически завершаются по конечной дате.
- Использование кода записывается атомарно с заказом. Скидка распределяется только по подходящим позициям; суммы строк точно сходятся с заказом. Отмена заказа не освобождает использованный промокод.
- Существующие коды нельзя переименовать. Удаление из формы отключает код, сохраняя историю. Конкурентное редактирование и применение требуют актуальных версий.

## Поддержка и возвраты

- `/support`: поиск и фильтры по типу и статусу, создание обращения с выбором заказа.
- Обращение содержит переписку и внутренние заметки. Последние 50 сообщений показываются в хронологическом порядке; предыдущие сообщения загружаются страницами. Покупатель через `/api/v1/support` имеет доступ только к собственным обращениям и публичным сообщениям. Личная поддержка и вопросы о товарах описаны в [переписках поддержки](support-conversations.md).
- Вопрос: `OPEN → IN_PROGRESS → CLOSED`, также доступно прямое закрытие нового вопроса.
- Возврат: `OPEN → IN_PROGRESS → APPROVED/REJECTED → CLOSED`. Одобрить можно сразу из `OPEN`. Активный возврат на один заказ может быть только один.
- Возврат оформляется на **весь доставленный/завершённый заказ**. Одобрение переводит заказ в `RETURN_REQUESTED`, без восстановления остатков. Закрытие одобренного возврата подтверждает фактический приём всех товаров, пригодных для повторной продажи, переводит заказ в `RETURNED` и восстанавливает остатки. Закрытие отклонённого возврата не меняет заказ.
- Частичные возвраты, утилизация повреждённых товаров и перечисление денег в этот процесс не входят. Подтверждение в интерфейсе явно объясняет смысл приёма товара.

## Покупатели, главная и модерация

`/customer-activity` содержит покупателей с заказами, отзывами или обращениями; карточка показывает общие показатели и последние 100 заказов, отзывов и обращений каждого типа. Это история действий внутри магазина, без отслеживания посещений сайта.

Главная показывает заказы за 7/30/90 дней, отмены по дате отмены, сумму размещённых заказов без отменённых/возвращённых, текущие обращения, обращения без действий сотрудника более 48 часов, опубликованные товары без остатка и модерацию старше 24 часов. Суммы не называются выручкой: получение денег провайдером не проверяется.

Очередь модерации сортируется по времени отправки. Есть фильтр ожидания 24/72 часа, режим по одному товару и шаблоны причин. При отклонении сохраняется снимок полей, вариантов, характеристик и фотографий; при повторной проверке показаны изменения относительно него. Для исторических отклонений без снимка интерфейс сообщает, что сравнение недоступно.

## Обновление базы

Перед запуском новой WebApi требуется миграция `20261020093201_AddAdminOperations`:

```powershell
dotnet ef database update --project src/Rozetka-clone/Infrastructure --startup-project src/Rozetka-clone/WebApi
```

Альтернатива для базы с предыдущими миграциями — идемпотентный [SQL](../scripts/sql/20261020-admin-operations.sql). Он добавляет версию акций, таблицы обращений/сообщений и снимков модерации; копирует CRUD-права существующих ролей приложения с `orders` и `products`. `PUBLIC` не получает новых прав. WebApi и AdminPanel обновляются вместе. Скрипт не меняет остатки и старые заказы. Откат миграции удаляет новые таблицы с данными: после начала работы используйте исправляющее обновление или резервную копию вместо удаления таблиц.

Штатное развёртывание выполняет `--migrate-admin-operations` в новом образе до остановки старого API. Команда проверяет владение схемой, применяет только явно разрешённые миграции и проверяет реальные чтения/права таблиц. Если у runtime-аккаунта нет DDL-прав, владелец базы должен выполнить SQL отдельно. Неожиданные старые миграции автоматически не применяются. Команда `--check-admin-operations-deployment` выполняет те же проверки без изменения схемы. Обе команды завершаются до запуска HTTP и фоновых обработчиков.

## Проверки

```powershell
dotnet test src/Rozetka-clone/WebApi.Tests/WebApi.Tests.csproj --configuration Release
# Для PostgreSQL используйте отдельную тестовую базу:
$env:TREBA_TEST_POSTGRES = '<development/test connection>'
dotnet test src/Rozetka-clone/WebApi.Tests/WebApi.Tests.csproj --configuration Release
```

Тесты проверяют цены на сервере, изоляцию продавцов и покупателей, переходы/версии, повторные действия, промокоды и распределение скидок, резервирование и его истечение, приём возврата, внутренние заметки, сравнение карточек, HTTP-права, PostgreSQL-транзакции и конфликты остатков. PostgreSQL-проверки создают уникальные таблицы с префиксом `treba_qa_` и удаляют только их; не направляйте тесты в рабочую базу.
